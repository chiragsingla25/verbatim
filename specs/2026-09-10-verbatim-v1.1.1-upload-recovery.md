# Spec addendum — Verbatim v1.1.1: upload-lifecycle recovery

Build contract for app-developer, extending v1 (`specs/2026-09-07-verbatim.md`) and v1.1
(`specs/2026-09-09-verbatim-v1.1.md`), both frozen build records. Same architecture, stack, and
deployment — Vite + React SPA on GitHub Pages, Supabase Postgres + pgvector + Auth + Storage +
Edge Functions. **No `/ask` pipeline change, no new architecture pattern.** One new Edge
Function (a thin GitHub-dispatch trigger, same shape as `ingest-dispatch`). Phases are hard
gates: implement one, run its checkpoint, stop for approval.

Delivery model: single generalist developer + a fresh-context `/code-review` at each phase
boundary — this adds a `SECURITY DEFINER` destructive RPC (`delete_manual_version`) and an
Edge Function that can start GitHub Actions runs, so it is authz-sensitive.

---

## Problem

A contributor or admin uploads a manual → `manual_versions` row at `status = 'pending'` with an
`ingest_jobs` row that moves `queued → parsing → review | failed`. The review screen
(`src/routes/ReviewUpload.tsx`) exposes **Approve / Reject only, and only when
`job.state === 'review'`**. There is no way to:

- **retry** ingestion on a `failed` job (or one wedged at `parsing` past the watchdog),
- **replace** a wrong / bad-scan source PDF without re-entering the whole upload form,
- **delete** a junk or failed `pending` version.

Failed and abandoned uploads pile up in the library's "Your uploads in progress" with no
recovery path. (Live example this session: a cancelled ingestion run left a version stuck at
`parsing` with no button of any kind.)

## Scope — four recovery actions

All confirmed in intake 2026-09-10:

1. **Delete the version** — hard delete: the `manual_versions` row, its `document_chunks` and
   `ingest_jobs` (FK `ON DELETE CASCADE`), the `storage.objects` row for
   `v/<version_id>/source.pdf`, and an `audit_log` entry. Gone from every screen.
2. **Retry ingestion** — re-run Docling on the **already-uploaded** file. One click → a new
   `ingest_jobs` row + a fresh GitHub Actions run. No re-upload.
3. **Replace the source PDF** — upload a corrected file to the **same** version (same
   instrument / title / edition / year / attestation), then ingest it.
4. **Reject from any state** — the existing Reject action becomes available whenever
   `version.status = 'pending'`, not only at `job.state = 'review'`. (Reject already keeps the
   version row + writes `audit_log` + since `20260910120000` deletes the parsed chunks.)

**Who:** the version's **creator, or any admin** — mirrors `publish_manual_version` /
`reject_manual_version`'s `created_by = auth.uid() or auth_role() = 'admin'` check.

**Out of scope:** bulk actions; recovering an `active` or `archived` version (that is
archive / supersede's job — these actions reject any non-`pending` version); a version-history
/ undo trail for deletes; editing instrument/title metadata (a separate small feature); an
in-app view of GitHub Actions logs (we link out).

## Architect's decisions (flag in review if wrong)

- **One new Edge Function, `ingest-trigger`**, does the GitHub `repository_dispatch` for both
  Retry and Replace. The storage webhook (`20260908150000_storage_ingest_webhook.sql`) is
  `after insert on storage.objects` — **an overwrite does not re-fire it** — so Replace cannot
  lean on the webhook; the SPA calls `ingest-trigger` explicitly after the re-upload
  completes. Retry has no upload at all, so it needs the function regardless.
- **Delete is a `SECURITY DEFINER` RPC**, not an Edge Function. It removes the
  `manual_versions` row (cascade handles chunks + jobs) and the `storage.objects` row for the
  source path. The underlying storage blob may linger until Supabase's storage GC — acceptable
  for a $0 pilot with tens of manuals; a true Storage-API delete can be a later follow-up if
  it matters.
- **Re-upload URL** comes from the SPA calling
  `supabase.storage.from('manuals').createSignedUploadUrl('v/<id>/source.pdf', { upsert: true })`
  directly (not a new RPC). Phase 1 must confirm the `manuals` bucket policies let the
  version's creator overwrite that path (INSERT policy exists for the first upload; an
  overwrite is an UPDATE on `storage.objects` — add a policy if missing, in the same
  migration).
- **State gating** for the action set on the review screen, all requiring
  `version.status = 'pending'`:
  | latest `ingest_jobs.state` | actions shown |
  |---|---|
  | `review` | Approve · Reject · Replace · Delete |
  | `failed` / `rejected` | Retry · Replace · Reject · Delete |
  | `queued` / `parsing` | (running UI) — Retry · Delete appear only once
  `updated_at` is older than the watchdog budget (~20 min: "looks stuck") |
- **Confirm dialogs** on Delete ("Delete this version, its file, and everything ingestion
  extracted? This cannot be undone.") and Replace (file picker). Retry and Reject reuse the
  existing inline-confirm style.

## Prior art & scope rationale

This is the standard **failed-job row-actions** pattern from CI dashboards (GitHub Actions'
"Re-run jobs"), CMS media libraries (replace asset / delete asset), and upload widgets
(retry / remove). Table stakes: retry, replace, delete, each with a confirm, scoped to the
owner. Deliberately skipped as overkill for an internal pilot with a handful of contributors:
bulk selection, a trash/restore bin, delete approvals, and per-attempt history. Nothing here
is novel; the risk is entirely in the authz on the destructive paths, which the verification
plan targets.

## What v1 / v1.1 already provide (no change needed)

- `request_manual_upload` (`20260908130000_upload_rpc.sql`) — the RPC pattern to copy:
  `SECURITY DEFINER`, `set search_path = public`, explicit `auth.uid()` + role checks,
  `audit_log` write.
- `reject_manual_version` (`20260910120000_reject_discards_parse.sql`) — already
  creator-or-admin, already `status = 'pending'` guarded, already deletes chunks. "Reject from
  any state" is a **UI-only** change (drop the `job.state === 'review'` condition on the
  button); no RPC change.
- `dispatchToGitHub(repo, token, body)` in `supabase/functions/ingest-dispatch/handler.ts` —
  the exact `repository_dispatch` call `ingest-trigger` needs. Extract to
  `supabase/functions/_shared/github.ts` and import from both.
- `ingest-dispatch` handler — reference for: look up the version, check `status = 'pending'`,
  insert `ingest_jobs { state: 'queued' }`, dispatch, and roll the job to `failed` on a
  non-2xx dispatch.
- Secrets `GITHUB_DISPATCH_REPO` / `GITHUB_DISPATCH_TOKEN` are already set for
  `ingest-dispatch`; `ingest-trigger` reuses them.
- `ingest.yml` `client_payload` is `{ job_id, version_id, object_path }` —
  `ingest-trigger` sends the same shape; `ingest/run.py` needs no change.
- `document_chunks` / `ingest_jobs` FK `manual_versions (id) ON DELETE CASCADE` (confirmed
  `20260908120000_phase1_schema.sql`). No `query_log` rows reference a `pending` version
  (students can't ask against non-active versions). `audit_log.target` is free text, not an
  FK.
- `ReviewUpload.tsx` already polls `getReviewData` every 3 s while the job is non-terminal and
  now surfaces elapsed time + a failed state (this session's `782614d`).

## Phased build plan

### Phase 1 — server: delete RPC + `ingest-trigger` function

**Files**
- `supabase/migrations/20260910130000_manual_recovery.sql` **(new)**:
  - `delete_manual_version(p_version_id uuid)` — `SECURITY DEFINER`, `set search_path = public`.
    Authed; version exists; `created_by = auth.uid() or auth_role() = 'admin'`;
    **`status = 'pending'`** (else `raise 'only a pending version can be deleted'`
    `errcode 'check_violation'`). Then: `delete from storage.objects where bucket_id =
    'manuals' and name = 'v/' || p_version_id || '/source.pdf'`;
    `delete from public.manual_versions where id = p_version_id`;
    `insert into audit_log (actor_id, action, target, meta)
    values (auth.uid(), 'delete', 'manual_versions:' || p_version_id,
    jsonb_build_object('title', <title captured before delete>))`.
    `revoke all … from public, anon; grant execute … to authenticated`.
  - If the `manuals` bucket has no UPDATE policy for the version creator on
    `v/<id>/source.pdf`, add one here (mirror the existing INSERT policy in
    `20260908170000` / wherever the upload policy lives) so Replace's `upsert` works.
- `supabase/functions/_shared/github.ts` **(new)** — move `dispatchToGitHub` here;
  `ingest-dispatch/handler.ts` imports it (no behaviour change).
- `supabase/functions/ingest-trigger/` **(new)** — `index.ts` + `handler.ts` in the
  `ingest-dispatch` style. `POST { versionId }` with the caller's JWT (verify JWT — **not**
  `--no-verify-jwt`; this is a signed-in user, unlike the webhook). Handler:
  1. resolve the caller (`auth.getUser`) and their role;
  2. load the version with the **service** client; 404 if missing; refuse if
     `status !== 'pending'`; refuse if not (`created_by === caller` or role `admin`) →
     403;
  3. insert `ingest_jobs { version_id, state: 'queued' }`;
  4. `dispatchToGitHub(repo, token, { event_type: 'ingest', client_payload: { job_id,
     version_id, object_path: 'v/<id>/source.pdf' } })`;
  5. on non-2xx dispatch, set that job `failed` + return 502; else return `{ job_id }`.
  `deno test` for the pure handler: non-owner → 403, non-pending → 409, happy path inserts +
  dispatches, dispatch failure marks the job failed. Add to `pnpm test:functions`.
- `src/lib/api.ts` — `deleteVersion(id)` (`supabase.rpc('delete_manual_version', …)`);
  `retryIngest(id)` (`supabase.functions.invoke('ingest-trigger', { body: { versionId: id } })`);
  `reuploadSourceUrl(id)` → `createSignedUploadUrl('v/<id>/source.pdf', { upsert: true })`.

**Checkpoint (script, as the contributor + a second non-owner contributor):**
- `deleteVersion` on the contributor's own `failed` version → `manual_versions` row gone,
  `document_chunks` / `ingest_jobs` gone, `storage.objects` row for the path gone, one
  `audit_log` `delete` row. On an `active` version → rejected. As a non-owner
  non-admin → rejected.
- `retryIngest` on a `failed` own version → exactly one new `ingest_jobs` row (`queued`) and
  one new `ingest` Actions run dispatched; as a non-owner → 403, no job, no run.
- `reuploadSourceUrl` returns a URL; a PUT of new bytes to it succeeds for the owner.
- Local sweep: `pnpm test:functions` (new tests green) + `pnpm build`.

### Phase 2 — SPA: recovery actions on the review screen + library/admin

**Files**
- `src/routes/ReviewUpload.tsx` — replace the single `canDecide` block with a state-gated
  action bar per the table in *Architect's decisions*. `version.status === 'pending'` is the
  master gate. Actions:
  - **Retry ingestion** → `retryIngest(id)`; on success, resume polling (`getReviewData`
    picks up the new `queued` job).
  - **Replace PDF** → hidden `<input type="file" accept="application/pdf">`; on pick →
    `reuploadSourceUrl(id)` → PUT the file → `retryIngest(id)`. Show upload progress /
    disable while in flight.
  - **Reject** → `rejectVersion(id, reason)` (unchanged) — now shown for `failed` / `rejected`
    / `review`.
  - **Delete version** → confirm dialog → `deleteVersion(id)` → `navigate('/')`.
- `src/routes/Library.tsx` — in "Your uploads in progress", show the job state and, for
  `failed` rows, a **Delete** button (confirm → `deleteVersion` → refresh) plus the existing
  "Review →" link (which now carries the full action bar).
- `src/routes/Admin.tsx` (Manuals tab) — for `pending` rows (any `ingestState`), add
  **Delete** in the actions cell (admin acting on anyone's upload). Reuse the confirm.
- `src/lib/api.ts` — `adminListAllVersions` already returns `pending` rows; no change beyond
  Phase 1's additions.

**Checkpoint (browser):**
- As the contributor, on a `failed` upload: **Retry** kicks a new run and the screen returns
  to the running state; when it reaches `review`, Approve appears. **Replace** with a real
  public-domain PDF re-parses and reaches `review`. **Delete** removes it — it is gone from
  the library, "uploads in progress", and (as admin) the Admin Manuals tab; a second reload
  confirms no ghost row.
- As a different contributor, the failed upload shows **no** Retry/Replace/Delete.
- As admin, the Manuals tab **Delete** on someone else's `pending` row works and writes an
  Activity entry.
- `pnpm lint` + `pnpm test` + `pnpm build` green.

## Verification step (whole addendum — hand to release-qa)

1. **AuthZ:** a non-owner non-admin cannot `delete_manual_version` or `ingest-trigger` any
   version (RPC + function both refuse); neither touches an `active` or `archived` version;
   `ingest-trigger` requires a valid JWT (rejects anon).
2. **Delete is complete:** row, `document_chunks`, `ingest_jobs`, and the `storage.objects`
   row for `v/<id>/source.pdf` are all removed; an `audit_log` `delete` entry is written; the
   version disappears from Library, "uploads in progress", `/review/:id`, and Admin → Manuals.
3. **Retry / Replace are single-fire:** each produces exactly one new `ingest_jobs` row and
   one `repository_dispatch` (no double-trigger with the storage webhook); `getReviewData`
   follows the newest job.
4. **No pipeline regression:** `/ask`, embeddings, `match_chunks`, `ingest/run.py`, and the
   eval suite are untouched — `python evals/run_evals.py --quick` stays green.
5. **Local sweep:** `pnpm lint` + `pnpm test` + `pnpm test:functions` (incl. the new
   `ingest-trigger` authz tests) + `pnpm build` green.
6. **Ship:** `supabase functions deploy ingest-trigger`; `supabase db push`; merge to `main`
   → CI → `deploy.yml` → Pages. No `/ask` function change.

## Deviations from spec

*(app-developer appends during Build, release-qa during Verify. "None" if nothing diverged.)*

- **[phase 1] `delete_manual_version` cannot remove the storage object.** Supabase blocks
  direct DML on `storage.objects` even from a `SECURITY DEFINER` function ("Direct deletion
  from storage tables is not allowed. Use the Storage API instead."). The RPC now only drops
  the `manual_versions` row (+ FK cascade + audit); `deleteVersion` in `src/lib/api.ts` calls
  `supabase.storage.from('manuals').remove([...])` first, gated by a new **`manuals_delete_contrib`**
  DELETE policy (contributor/admin, and only for a *pending* version they own — name-matched by
  construction, no `split_part()::uuid`). Extra follow-up migration
  `20260910140000_manual_recovery_fix.sql`. Net effect unchanged (row, chunks, job, and object
  all gone) but delete is now a 2-call client orchestration, not one RPC. A direct PostgREST
  call to the RPC would leave the object orphaned — the Phase 2 UI always does both.
- **[phase 1] `_shared/github.ts` split done as planned;** `ingest-dispatch/index.ts` imports
  `dispatchToGitHub` from there, `handler.ts` no longer exports it, its 8 Deno tests unchanged
  and green.
- **[phase 1] Checkpoint fires real `ingest` Actions runs.** Creating a test version and
  uploading its stub PDF trips the Storage webhook; `ingest-trigger` tests dispatch too. These
  runs fail fast (stub PDF / deleted job row) and touch no corpus data — expected checkpoint
  noise, not a regression.
